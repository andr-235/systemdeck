# AGENTS.md

Постоянные инженерные правила разработки SystemDeck. Пайплайн работы агента
(выбор и вызов скиллов, порядок шагов) — `opencode.json` →
`agents.systemdeck.system`: это единственный источник процесса; здесь — правила,
которые действуют при любой работе.

## Источники правил

- Терминология — `CONTEXT.md`.
- Границы слоёв — `docs/architecture.md` + `docs/adr/0002`.
- Архитектурные решения — `docs/adr/`.
- Issues: создание — `docs/agents/create-issue.md`; обогащение backlog —
  `docs/agents/backlog-triage.md`; метки и states — `docs/agents/triage-labels.md`;
  работа через `gh` CLI — `docs/agents/issue-tracker.md`; контекстная модель —
  `docs/agents/domain.md`.
- Доступные скиллы — `.agents/skills/` + `skills-lock.json` (IDs path-derived,
  case-sensitive).

При конфликте инструкций не решай произвольно: остановись, укажи источник
противоречия и сообщи пользователю.

## Общие принципы

- Перед правкой изучи затронутый код, зависимости, контракты и существующие
  тесты.
- API, файлы, команды и возможности библиотек подтверждай по репозиторию,
  а не по памяти.
- Scope задачи расширяй только с обоснованием в PR.
- Противоречие с ADR сначала фиксируй (issue/PR), затем решай.

## Архитектура

Четыре слоя (ADR-0002): **Main** — системные операции, ОС, Electron, жизненный
цикл; **Preload** — минимальный безопасный мост `contextBridge`; **Renderer** —
React, взаимодействие и визуализация; **Shared** — типизированные контракты и
константы без Electron/Node runtime.

Правила границ:

- Renderer импортирует только `shared` и свои модули; к системным ресурсам —
  только через Application API (`window.api`).
- Системная логика живёт в Main; React-компоненты её только вызывают.
- IPC-контракты и идентификаторы каналов определены один раз в `shared/ipc`
  и используются обеими сторонами.
- Privileged API расширяется только реальным требованием задачи.
- Циклические зависимости между слоями и фичами отсутствуют.

## Структура и рефакторинг

- Одна файл-одна ответственность; компонент отвечает за одну задачу.
- Независимую логику держи в hooks, services, utilities или специализированных
  модулях; данные, обработка, состояние и визуализация живут раздельно.
- Универсальные модули с несвязанными функциями и дублирование существующих
  реализаций — признак того, что структура требует пересмотра.
- Абстракции вводи только под конкретное текущее использование.
- Реэкспорт через barrel `index.ts` не используй: импорты идут по путям файлов.
- Публичные контракты сохраняй при рефакторинге, если их изменение не
  согласовано задачей.

Рефакторинг завершён, когда код стал проще, поведение сохранено и проверки
проходят.

## TypeScript

- `any`, необоснованные type assertions и `@ts-ignore` — признак недостающего
  типа; исправляй причину, а не подавляй ошибку.
- Явные типы — на границах модулей и IPC; `null`/`undefined` и отказ системных
  API обрабатывай явно.
- Shared-контракты независимы от Electron runtime.

## React и интерфейс

- Функциональные компоненты и hooks; системная логика — вне JSX.
- Состояние, которое вычисляется из имеющихся данных, храни вычисленным.
- Каждое интерактивное действие имеет реальный обработчик; декоративные кнопки
  без функциональности не добавляй.
- Для данных и операций предусматривай loading, empty, error и unavailable
  состояния.
- Соблюдай существующую дизайн-систему, читаемость при изменении размера окна.
- Вымышленные метрики не показывай как реальные.

## Electron и безопасность

- Сохраняй `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`.
- Каждый IPC-обработчик валидирует входные данные; произвольные команды
  Renderer → Main не передаются.
- Пароли, токены и другие секреты не попадают в Application Log; Log Redaction
  не обходится.
- Удаление файлов и завершение процессов — только с защитными проверками.
- Привилегии не повышаются без явного требования задачи; проверки безопасности
  не отключаются ради прохождения сборки.

## Планирование

Перед любыми правками `src/`:

1. Прочитай issue и комментарии.
2. Изучи связанный код и ADR.
3. Вызови необходимые скиллы через Skill tool.
4. Создай план по шаблону `create-implementation-plan` в
   `plan/[purpose]-[component]-1.md`, свяжи его с issue и упомяни в PR.
5. Зафиксируй объём, зависимости, риски и проверяемые критерии.

Правка `src/` без план-файла считается незавершённой работой.

## Тестирование и проверки

- Тесты colocated, рядом с тестируемой функциональностью; импорты — по путям
  файлов, без barrel-реэкспортов.
- Исправление бага сопровождай регрессионным тестом.
- Мокай внешние и системные зависимости; покрывай не только успех, но и ошибки,
  отказ доступа и недоступность данных.
- Тесты не удаляй и не ослабляй ради зелёного результата.

Основная проверка — `npm run check` (lint, format, boundaries, file-size,
typecheck, test). При изменениях в Main, Preload, IPC или запуске Electron
дополнительно выполняй `npm run smoke`. Если проверку выполнить нельзя —
укажи причину; результаты незапущенных проверок не выдавай за фактические.

## GitHub Issues, PR и коммиты

- Источник задач — GitHub Issues `andr-235/systemdeck` через `gh` CLI;
  новые задачи стартуют с `needs-triage`, работу начинай с `ready-for-agent`
  или по прямому указанию пользователя.
- `ready-for-human` на issue — задача для ручной реализации человеком; на PR —
  ожидание ручного ревью.
- Перед созданием issue проверяй существующие задачи и дубликаты; новые
  labels автоматически не создавай.
- Issue закрывается только после реализации, подтверждённого дубликата или
  согласованного решения.
- PR, закрывающий issue, начинает тело с `Closes #N` (английское ключевое
  слово). В описание добавь план, изменённые компоненты, результаты проверок
  и строку `Skills: id1, id2` — она дополняет, но не заменяет реальные вызовы
  Skill tool.
- Merge — только с одобрения или прямого разрешения; `git push --force`
  не используется.
- Коммиты на русском, формат `type: краткое описание`:
  `feat: добавить мониторинг памяти`, `fix: исправить обновление метрик`,
  `refactor: разделить логику карточки процессора`, `test: добавить проверки
IPC`, `docs: обновить инструкции агента`.

## Автоматические гейты и ручные правила

Блокируют PR автоматически (входят в `npm run check`): `check:boundaries`
(границы слоёв), `check:file-size` (80 строк кода в Renderer `.tsx`, кроме
тестов; существующие превышения зафиксированы в
`scripts/file-size-baseline.json` и не растут), typecheck, lint, format, test.

Ручные правила (проверяй перед коммитом): план-файл, одна ответственность на
файл, отсутствие дублирования и заглушек, наличие обработчиков у интерактивных
действий.

## Критерии завершения

Задача завершена, когда: выполнены критерии приёмки issue; соблюдены границы
архитектуры; создан план; есть квитанции обязательных Skill-вызовов; изменения
покрыты тестами; `npm run check` (и `npm run smoke` при изменениях
Main/Preload/IPC) выполнен фактически; PR содержит описание, проверки и список
скиллов. Заглушки вместо функциональности и отключённые проверки — задача
не завершена.
