# Кэшированное сэмплирование процессов: дельта по последнему сэмплу вместо двух WMI-запросов

EPIC 3 (модуль «Процессы»). Первая версия `ProcessMonitor` считала CPU% процесса по дельте двух последовательных WMI-запросов `Win32_Process` с паузой `sampleGapMs` (1000 мс) внутри каждого такта `read()`; process-loop при этом тикает раз в 5 с. Итог — до 6 с задержки между запросами Renderer и данными, и два WMI-запроса за такт. Решили: `ProcessMonitor` хранит предыдущий сэмпл и на каждом такте делает один WMI-запрос, считая дельту `UserModeTime+KernelModeTime` с сохранённым сэмплом. Задержка уходит, нагрузка на WMI падает вдвое.

## Considered Options

- **Dual-request (статус-кво)**: два запроса внутри такта; окно выборки известно точно (`sampleGapMs`), но задержка до 6 с и двойная нагрузка.
- **Cached-дельта (выбрано)**: один запрос на такт; окно выборки = интервал такта (~5 с). Процесс, исчезнувший между сэмплами, пропускается (CPU% не выдумывается).

## Consequences

- Первый сэмпл после старта не имеет предыдущего — `cpuPercent` для него `null` (Unavailable), как первый CPU Snapshot (прочерк в UI). Для этого контрактное поле `ProcessEntry.cpuPercent` расширено до `number | null` — это осознанное расширение скоупа #32 (исходно «контракт не меняется»), согласованное в гриле: репозиторий не выдумывает метрики (Unavailable-правило в CONTEXT.md), `0` на первом сэмпле было бы выдуманным числом.
- Регресс счётчиков WMI (отрицательная дельта `UserModeTime+KernelModeTime`, сброс при перезагрузке службы/перемотке тиков) тоже отдаёт `null`, а не `0` — аналог `CpuMonitor`, где отрицательная дельта → `null`.
- Пустой сэмпл `withFallback` по-прежнему сохраняется как «предыдущий»: потеря одного такта не ломает дельту следующего.
